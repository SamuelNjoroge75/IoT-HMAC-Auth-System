# Phase 2 — HMAC-Secured Server (Mitigation Phase)

## Overview
This phase integrates HMAC-SHA256 into both the server and client to
secure the MAC-address-only authentication and mitigate the vulnerability demonstrated in Phase 1. The secret key is pre-shared and stored locally on both sides hence it is never transmitted over the network. 
The attacker from Phase 1 repeats its attack against this secured server and is rejected on every attempt.

## Files
- 'HMAC-IoT-server/HMAC_server.py' — Flask server that verifies both MAC address and HMAC-SHA256 signature
- 'HMAC-IoT-server/key_generator.py' — generates a random secret key
  and registers it against a device MAC address in 'device_keys.json'
- 'HMAC-IoT-client/HMAC_IoT_device.py' — legitimate IoT client signing each request with HMAC-SHA256 before sending
- 'Attacker/HMAC_attacker.py' — sends forged requests using two
  bypass methods: no signature and fake signature

## Setup

### Ubuntu Server VM
1. Generate the device's secret key (run once):
```bash
   python3 key_generator.py
```
2. Install dependencies:
```bash
   pip3 install flask
```
3. Run the server:
```bash
   python3 HMAC_server.py
```
4. Server listens on 'server's IP Address:5000'

### Kali 1 VM (Legitimate Client)
1. Copy the secret key generated by 'key_generator.py' into
   'HMAC_IoT_device.py'
2. Install dependencies:
```bash
   pip3 install requests
```
3. Run the client:
```bash
   python3 HMAC_IoT_device.py
```

### Kali 2 VM (Attacker)
1. Set 'spoofed_mac_address' in 'HMAC_attacker.py' to the MAC address
   discovered via Nmap in Phase 1.
2. Run the attacker:
```bash
   python3 HMAC_attacker.py
```

## Expected Results
- Legitimate client: all requests 'ACCEPTED' — signatures verified successfully
- Attacker (no signature): 'BLOCKED'
- Attacker (fake signature): 'BLOCKED'
- Attacker (replayed signature): 'BLOCKED'
- Attack success rate: 0%

## Key Security Property
The attacker knows the legitimate MAC address (discovered via Nmap in
Phase 1) but cannot produce a valid HMAC signature without the secret
key. The server uses `hmac.compare_digest()` for signature comparison
to prevent timing-based attacks on the verification step itself. Every rejected attempt is logged with an `ALERT` flag in `HMAC_system.log`, distinguishing forged traffic from legitimate traffic hence mitigates the attack unlike the vulnerable server in Phase 1.
